# RAG 重构方案分析：从向量检索到 LLM Wiki

> 写作日期：2026-05-03
> 背景：当前 RAG 系统准确性不足，需要评估重构方向
> 硬约束：全部本地运行，单 RTX 3090，Qwen 模型（可换但 GPU 不变）

---

## 一、当前系统问题诊断（基于实测）

### 1.1 实测案例

**查询**："在PVE虚拟机里怎么安装NVIDIA驱动让Docker能用显卡？"

**源文档** (`log-DEPLOY-P1-infrastructure.md`) 实际包含：
1. PVE 打快照
2. `sudo apt update && sudo apt upgrade -y`
3. `ubuntu-drivers devices` → `sudo ubuntu-drivers autoinstall`
4. 重启，`nvidia-smi` 验证
5. Docker 官方脚本安装
6. NVIDIA Container Toolkit 4步安装
7. `docker run --rm --gpus all ubuntu nvidia-smi` 验证

**Qwen 回答的问题**：
- 编造了"确保CPU支持VT-d或AMD-Vi技术"（源文档无此内容）
- 篡改命令为 `sudo apt install nvidia-driver-580-server`（原文是 `ubuntu-drivers autoinstall`）
- 遗漏了 NVIDIA Container Toolkit 的完整安装步骤
- 声称"笔记中未提供Docker安装命令"然后自己编造（原文明确给了官方脚本）

### 1.2 问题归因

| 环节 | 表现 | 严重程度 |
|---|---|---|
| 向量检索 | 正确文档排第2（relevance=0.46），第1是主题相近但场景不同的文档 | 中 |
| 500字截断 | 文档后半部分（Container Toolkit）完全丢失 | 高 |
| 模型幻觉 | Qwen 编造源文档没有的内容，篡改命令 | **极高** |

**结论**：三个问题叠加导致不可用。其中模型幻觉是根本瓶颈——即使检索和截断都修好，Qwen 仍然可能编造。

## 二、关键概念解释

### 2.1 向量（Vector）在 RAG 中的含义

向量就是一组数字，比如 `[0.12, -0.45, 0.78, ..., 0.33]`（通常 384 或 768 个数字）。

**核心思想**：意思相近的文字，生成的数字数组也接近。"人工智能"和"AI"的向量很接近；"人工智能"和"红烧肉"的向量差很远。

**在 RAG 中的用途**：
1. 把每篇文档转成一个向量（叫 embedding）
2. 用户提问也转成一个向量
3. 在数据库里找距离最近的文档向量 = 找最相关的文档

**局限**：一篇 3000 字的文章被压缩成 384 个数字，细节全丢了。就像把一本书的内容概括成一句话——你知道大概讲什么，但找不到具体第几页第几段。

### 2.2 Chunking（分块）

把一篇长文档切成多个小段，每段单独生成向量。

**好处**：大文件的细粒度内容可以被单独检索到。
**当前系统没有做 chunking**——每个 .md 文件就是一个向量。

### 2.3 LLM Wiki 的原理

和向量搜索完全不同：

```
向量搜索：用户提问 → 找相似文档 → 给LLM看片段 → LLM临时回答
LLM Wiki：源文档 → LLM预先读完并整理成wiki → 用户提问 → LLM看wiki回答
```

**本质区别**：向量搜索是"临时开卷考试"，Wiki 是"考前已经做好了完整笔记"。

## 三、方案一：RAG 改进

### 3.1 目标

在现有架构（ChromaDB + BGE embedding + Qwen）基础上修复已知问题，提升准确性。

### 3.2 改进项

#### 改进 1：去掉 500 字截断（影响：高，工作量：低）

**现状**：检索到文档后只取前 500 字给 Qwen。
**改进**：将完整文档内容传递给 Qwen，或至少扩大到 3000-5000 字。
**风险**：Qwen 32B 的上下文窗口是 32K token，一篇文档通常 1000-3000 字（约 1500-4500 token），5 篇文档最多 ~22K token，仍在窗口内。但如果 top_k 更大或多篇长文档，可能接近上限。

**代码改动**：`services/rag/app/rag_engine.py` 第 193 行，`snippet` 生成逻辑。

#### 改进 2：添加 Chunking（影响：高，工作量：中）

**现状**：每篇 .md 文件 = 一个向量。
**改进**：按段落或固定长度切分，每个 chunk 单独生成向量。
**策略**：
- 按 `##` 或 `###` 标题切分（保留语义完整性）
- 每个 chunk 上限 500-800 字
- 重叠 100 字（避免边界丢失信息）
- chunk 的 metadata 继承父文档的 path、title、tags、loa_min

**代码改动**：`rag_engine.py` 的 `index_vault()` 方法，新增 `_chunk_document()` 函数。

#### 改进 3：基于 mtime 的增量索引（影响：中，工作量：低）

**现状**：只检查文件是否已索引（by path），修改过的文件不会更新。
**改进**：比较文件的 `mtime` 和索引中存储的 `mtime`，不一致则重新索引。

**代码改动**：`rag_engine.py` 第 126 行的跳过逻辑。

#### 改进 4：改进检索策略（影响：中，工作量：中）

**现状**：纯向量搜索，top_k * 3 过取后 LOA 过滤。
**改进**：
- **混合搜索**：向量搜索 + BM25 关键词搜索，结果融合排序
- **元数据预过滤**：先按 tags 筛选缩小范围，再向量搜索
- **重排序（Re-ranking）**：用交叉编码器对 top 结果重新排序

#### 改进 5：改进 Prompt（影响：中，工作量：低）

**现状**：简单的中文 prompt，要求基于笔记回答。
**改进**：
- 明确要求"只使用提供的上下文回答，不要添加上下文中没有的信息"
- 如果上下文不足以回答，要求明确说"根据现有资料无法确定"
- 添加来源引用要求

### 3.3 预期效果

| 改进项 | 解决的问题 | 预期改善 |
|---|---|---|
| 去截断 | 信息丢失 | 显著——Qwen 能看到完整文档 |
| Chunking | 大文件检索不精确 | 显著——细粒度匹配 |
| mtime 检测 | 修改不更新 | 完全解决 |
| 混合搜索 | 语义漂移 | 中等——关键词兜底 |
| Prompt 优化 | 模型幻觉 | 有限——取决于模型能力 |

### 3.4 局限性

**核心局限**：即使所有改进都做了，Qwen 32B 仍然可能在以下情况幻觉：
- 上下文信息矛盾时（多篇文档说法不一）
- 上下文信息不足时（问题超出检索到的文档范围）
- 需要跨文档综合推理时

RAG 改进能**减少**幻觉，但不能**消除**幻觉。

### 3.5 工作量估算

| 改进项 | 工作量 | 优先级 |
|---|---|---|
| 去截断 | 0.5 天 | P0 |
| Prompt 优化 | 0.5 天 | P0 |
| mtime 检测 | 0.5 天 | P1 |
| Chunking | 2-3 天 | P1 |
| 混合搜索 | 3-5 天 | P2 |
| 重排序 | 2-3 天 | P2 |
| **总计** | **约 2 周** | |

## 四、方案二：LLM Wiki

### 4.1 目标

采用 Karpathy 提出的 Wiki 模式：LLM 预先阅读源文档，生成结构化的 wiki 页面，查询时基于 wiki 回答。

### 4.2 架构设计

```
┌─────────────────────────────────────────────────┐
│                  三层架构                          │
│                                                   │
│  Layer 1: 源文档（Vault，1,800+ 篇 .md）          │
│  ├─ 只读，LLM 不修改                               │
│  ├─ 持续增长的原始知识                              │
│                                                   │
│  Layer 2: Wiki（LLM 生成的结构化页面）              │
│  ├─ index.md — 目录索引                            │
│  ├─ entity/ — 实体页（项目、工具、人物）             │
│  ├─ concept/ — 概念页（技术概念、方法论）            │
│  ├─ source/ — 源文档摘要页                         │
│  ├─ synthesis/ — 综合分析页                        │
│  └─ log.md — 操作日志（追加写入）                   │
│                                                   │
│  Layer 3: Schema（LLM 行为规范）                   │
│  ├─ 定义 wiki 结构和命名规范                       │
│  ├─ 定义 ingest/query/lint 操作流程                │
│  └─ 类似 CLAUDE.md 的角色                         │
└─────────────────────────────────────────────────┘
```

### 4.3 三个核心操作

#### 操作 1：Ingest（入库）

```
新文档加入 Vault
  → LLM 读取全文
  → 生成 source/ 摘要页
  → 更新/创建相关的 entity/ 和 concept/ 页面
  → 更新 index.md
  → 追加 log.md
```

**关键**：LLM 在入库时读完全文，有充足时间理解。一篇源文档可能需要更新 5-10 个 wiki 页面。

**时间成本**：一篇 2000 字的文档，Qwen 32B 处理约需 30-60 秒（读取 + 生成多个页面）。

#### 操作 2：Query（查询）

```
用户提问
  → LLM 读 index.md（目录）
  → 判断需要读哪几个 wiki 页面
  → 读取相关页面
  → 综合回答（带来源引用）
```

**时间成本**：读 index.md (<1s) + LLM 推理选页面 (~2s) + 读 3-5 个页面 (<1s) + LLM 生成回答 (~10-20s) = **总计 15-25 秒**。

#### 操作 3：Lint（健康检查）

```
定期执行
  → 检查页面间矛盾
  → 标记过时内容
  → 发现孤立页面（无交叉引用）
  → 建议补充内容
```

### 4.4 面临的挑战

#### 挑战 1：1,800 篇文档的全覆盖

**问题**：1,800 篇全部生成 wiki 页面，工作量巨大。
**估算**：
- 每篇源文档平均需要 LLM 处理 30-60 秒
- 1,800 篇 × 45 秒 = 约 22.5 小时连续 GPU 推理
- 加上交叉引用更新，实际可能需要 40-60 小时

**缓解方案**：
- 分批处理（每天处理 100 篇，约 2 周完成）
- 优先处理高价值文档
- 增量处理（新文档入库时自动生成 wiki）

#### 挑战 2：Qwen 32B 的能力限制

**问题**：Wiki 质量直接取决于 LLM 的理解能力。Qwen 32B 能否胜任？

**评估**：
- 单文档摘要：**能胜任**，这是 Qwen 的强项
- 交叉引用识别：**有风险**，需要判断两篇文档是否在说同一件事
- 矛盾检测：**有风险**，需要跨文档对比推理
- 综合回答：**取决于上下文质量**，如果 wiki 页面本身质量高，回答质量也会高

**缓解方案**：
- 初期人工审核 wiki 质量
- 分阶段上线（先做 source 摘要页，再做 entity/concept 页）
- 保留源文档作为 fallback

#### 挑战 3：维护成本

**问题**：源文档更新后，wiki 页面需要同步更新。
**方案**：
- 监听 Vault 文件变更（inotify 或定时扫描）
- 变更触发增量 ingest
- 更新受影响的 wiki 页面和交叉引用

#### 挑战 4：查询延迟

**问题**：每次查询需要 15-25 秒，比向量搜索慢 100 倍。
**缓解**：
- index.md 预加载到内存
- wiki 页面文件很小（<1KB），读取几乎无延迟
- 真正的瓶颈是 LLM 生成回答的 GPU 推理时间，无法避免

### 4.5 预期效果

| 维度 | 预期改善 |
|---|---|
| 准确性 | 显著提升——LLM 基于自己整理的内容回答，幻觉大幅减少 |
| 完整性 | 显著提升——wiki 页面是全文摘要，不丢失信息 |
| 交叉引用 | 新增能力——预先建立文档间关联 |
| 知识积累 | 新增能力——好的回答可以回写 wiki |
| 查询速度 | 下降——从 <1s 变为 15-25s |

### 4.6 工作量估算

| 阶段 | 内容 | 工作量 |
|---|---|---|
| Schema 设计 | wiki 结构、命名规范、操作流程 | 2 天 |
| Ingest 引擎 | LLM 读取 + 生成 wiki 页面 + 更新 index | 5-7 天 |
| Query 引擎 | index 查找 + 页面读取 + LLM 回答 | 3-5 天 |
| 增量更新 | 文件变更监听 + wiki 同步 | 3-5 天 |
| Lint 引擎 | 矛盾检测、过时标记、孤立页面 | 3-5 天 |
| Web UI | 查询界面、wiki 浏览 | 3-5 天 |
| 测试调优 | 质量验证、prompt 优化 | 5-7 天 |
| **总计** | | **约 4-6 周** |

## 五、方案三：混合方案

### 5.1 子方案 A：RAG 为主 + Wiki 补充

```
┌─────────────────────────────────────────────┐
│  查询流程                                     │
│                                               │
│  用户提问                                      │
│    → 向量搜索（快，<1s）                       │
│    → 如果置信度高（relevance > 0.7）            │
│    →   直接用 RAG 结果回答                      │
│    → 如果置信度低（relevance < 0.7）            │
│    →   转 wiki 查询（慢，15-25s）               │
│    →   wiki 结果更准确                          │
│                                               │
│  Wiki 覆盖范围：高价值文档子集（200-500 篇）    │
│  RAG 覆盖范围：全部 1,800+ 篇                  │
└─────────────────────────────────────────────┘
```

**优点**：
- 简单问题快速回答（向量搜索 <1s）
- 复杂/低置信度问题走 wiki，准确性有保障
- Wiki 只需覆盖高价值子集，工作量可控

**缺点**：
- 两套系统维护
- 置信度阈值需要调优
- RAG 的幻觉问题仍然存在（只是在高置信度场景下风险较低）

### 5.2 子方案 B：Wiki 为主 + RAG 辅助

```
┌─────────────────────────────────────────────┐
│  查询流程                                     │
│                                               │
│  用户提问                                      │
│    → 先查 wiki index.md                       │
│    → 如果 wiki 有覆盖                          │
│    →   读 wiki 页面回答（准，15-25s）            │
│    → 如果 wiki 没覆盖                          │
│    →   fallback 到向量搜索（快但可能不准）       │
│                                               │
│  Wiki 覆盖范围：逐步扩大到全部文档              │
│  RAG 覆盖范围：wiki 未覆盖的文档               │
└─────────────────────────────────────────────┘
```

**优点**：
- 准确性优先——wiki 覆盖的部分回答质量高
- 逐步迁移——可以先覆盖核心文档，再扩大
- RAG 作为 fallback 保证全覆盖

**缺点**：
- 初期大部分查询仍走 RAG（wiki 覆盖率低）
- 需要维护 wiki 和 RAG 两套索引
- Wiki 建设周期长（1,800 篇全量需要 4-6 周）

### 5.3 子方案 C：RAG + Wiki 融合（推荐）

不维护两套独立系统，而是**将 wiki 思想融入 RAG**：

```
┌─────────────────────────────────────────────────┐
│  融合架构                                         │
│                                                   │
│  入库阶段（Ingest）：                              │
│    源文档 → LLM 生成摘要/结构化内容                 │
│    → 将摘要（而非原文）embedding 入向量库           │
│    → 同时保留原文作为 LLM 回答时的补充上下文        │
│                                                   │
│  查询阶段（Query）：                               │
│    用户提问 → 向量搜索（在摘要上搜索，更精确）      │
│    → 检索到相关摘要                                │
│    → 读取对应源文档的完整内容（不截断）              │
│    → LLM 基于完整内容回答                          │
│                                                   │
│  本质：用 LLM 预处理提升检索质量，                  │
│        但不维护独立的 wiki 页面体系                 │
└─────────────────────────────────────────────────┘
```

**优点**：
- 只有一套系统（向量库），维护简单
- 摘要比原文更精炼，检索更准
- 回答时仍基于完整原文，不丢失信息
- 不需要维护 wiki 页面间的交叉引用

**缺点**：
- 没有 wiki 的交叉引用和知识积累能力
- 入库时需要 LLM 处理，首次建索引较慢
- 摘要质量取决于 Qwen 的能力

## 六、综合推荐：单 3090 最优方案

### 6.1 约束条件

| 约束 | 值 |
|---|---|
| GPU | 单 RTX 3090（24GB 显存） |
| 模型 | Qwen 32B AWQ（~18GB 显存占用） |
| 文档量 | 1,800+ 篇 .md |
| 隐私 | 100% 本地，不走任何 API |
| 优先级 | 准确性 > 速度 |

### 6.2 推荐方案：渐进式融合

**第一阶段（1-2 周）：RAG 止血**

立即修复现有 RAG 的致命问题：
1. 去掉 500 字截断，传递完整文档
2. 优化 prompt，要求模型忠实于上下文
3. 修复 mtime 增量索引
4. 重新测试，评估改善程度

**第二阶段（2-4 周）：入库预处理**

引入 wiki 思想的核心部分——入库时 LLM 预处理：
1. 入库时用 Qwen 为每篇文档生成结构化摘要
2. 摘要 embedding 入向量库（替代原文 embedding）
3. 查询时：向量搜索摘要 → 找到对应原文 → 读取完整原文 → Qwen 回答
4. 首次建索引需要 LLM 处理 1,800 篇（约 20-30 小时 GPU 推理，可分批进行）

**第三阶段（4-6 周）：增量 Wiki 层**

在预处理基础上，逐步建设轻量级 wiki：
1. 为高价值主题（项目、核心概念）生成 wiki 页面
2. 维护 index.md 作为结构化目录
3. 查询时：先查 wiki → 有则用 wiki 回答 → 无则 fallback 到 RAG
4. 新文档入库时自动触发 wiki 更新

**第四阶段（持续）：写入与实时更新**

实现你描述的愿景：
1. 自然语言写入（"今天下午3点前要提交报告" → 写入 daily note）
2. 写入后自动更新索引（向量 + wiki）
3. 多客户端访问同一知识库

### 6.3 为什么这个方案最强

| 维度 | 说明 |
|---|---|
| **准确性** | 入库预处理让 Qwen 提前理解文档，查询时基于预处理结果回答，幻觉大幅减少 |
| **完整性** | 查询时读取完整原文（不截断），不丢失信息 |
| **速度** | 简单查询：向量搜索摘要 <1s + 读原文 <1s + Qwen 回答 10-15s = 约 15s；复杂查询走 wiki：20-30s |
| **可维护性** | 一套向量库为主，wiki 为辅，不过度复杂 |
| **可扩展** | 新文档入库自动预处理，增量 wiki 更新 |
| **可行性** | 全部基于现有技术栈（ChromaDB + Qwen），不需要引入新依赖 |

### 6.4 关于多 GPU

你说得对——换双 3090 甚至更多 GPU，理论上确实更强：
- 可以跑更大的模型（如 Qwen 72B），模型能力越强幻觉越少
- 可以并行处理入库预处理，速度翻倍
- 可以同时跑 embedding 模型和生成模型，不互相阻塞

但当前单 3090 方案已经可以通过"入库预处理"弥补模型能力的不足。多 GPU 是锦上添花，不是必须。

### 6.5 速度预期

| 查询类型 | 预期响应时间 | 说明 |
|---|---|---|
| 简单事实查询 | 10-15 秒 | 向量搜索 + 读原文 + Qwen 回答 |
| 复杂综合查询 | 20-30 秒 | 可能需要读多篇原文 + wiki 综合 |
| 首次入库（单篇） | 30-60 秒 | LLM 预处理 + embedding |
| 批量重建索引 | 20-30 小时 | 1,800 篇全量预处理，分批进行 |

**这个速度够用吗？** 对于"准确性第一"的需求来说，10-30 秒的回答延迟是完全可接受的。你等一个靠谱的答案等 15 秒，远好于等 1 秒拿到一个编造的答案。

## 八、深度追问：Wiki 的本质与你的理想架构

### 8.1 你的三个问题的回答

**问题 1：Wiki LLM 的诱人之处是不是它会持续维护 wiki 文件夹，越用越强？**

**是的，但有条件。**

Wiki 的"持续成长"体现在两个层面：

| 成长类型 | 机制 | 条件 |
|---|---|---|
| **广度成长** | 新文档入库 → 生成新 wiki 页面 → 知识库扩大 | 需要有 ingest 流程触发 |
| **深度成长** | 用户提问 → 好的回答被回写为 wiki 页面 → 知识被沉淀 | 需要有 write-back 机制 |

关键区别：
- **向量搜索不会成长**——每次查询都是独立的，上一次查询的结果不会帮助下一次
- **Wiki 会成长**——好的查询结果被沉淀为 wiki 页面，下次查询直接可用

但"越用越强"不是自动的。需要：
1. 每次 ingest 新文档时触发 wiki 更新
2. 每次有价值的查询结果被主动回写
3. 定期 lint 维护一致性

**问题 2：Wiki LLM 不修改 raw 文件，Obsidian Vault 只是 readonly input？**

**在 Karpathy 的原始设计中，是的。** 三层分离：

```
Layer 1: 源文档（Vault）    → 只读，LLM 不碰
Layer 2: Wiki（LLM 生成）   → LLM 完全拥有
Layer 3: Schema（规范）     → 定义 LLM 行为
```

但这里有一个关键洞察——**你的 Obsidian Vault 本身就已经是 wiki 了**。

你用 Obsidian 管理 PKB，里面已经有 wiki-links、tags、PARA 结构。Vault 不是一个"原始文档堆积场"，它本身就是一个有组织的知识库。所以对你来说：

```
Karpathy 的场景：         你的场景：
原始文档（论文/网页）      Obsidian Vault（已经是结构化的）
  ↓ ingest                  ↓ ingest
Wiki（LLM 整理版）        Wiki（可以就写在 Vault 里）
```

**问题 3：能否建立 raw 为中心、读写共享的单一文件夹？**

**可以，而且这正是最适合你的方案。**

你的愿景：
```
┌─────────────────────────────────────────────────┐
│  单一知识库（Obsidian Vault）                      │
│                                                   │
│  原始笔记（人写的）                                │
│  ├── 1_PROJECT/                                   │
│  ├── 2_AREA/                                      │
│  ├── 3_RESOURCE/                                  │
│  └── 4_ARCHIVE/                                   │
│                                                   │
│  AI 增强层（LLM 写的，人可以编辑）                 │
│  ├── _wiki/                                       │
│  │   ├── index.md          （目录索引）            │
│  │   ├── entity/           （实体页）              │
│  │   ├── concept/          （概念页）              │
│  │   └── synthesis/        （综合分析）            │
│  └── _schema/                                     │
│      ├── ingest.md         （入库规范）            │
│      ├── query.md          （查询规范）            │
│      └── lint.md           （维护规范）            │
│                                                   │
│  → Obsidian 读写同一个文件夹                       │
│  → AI 系统读写同一个文件夹                         │
│  → 一切 human-readable markdown                   │
└─────────────────────────────────────────────────┘
```

**核心循环**："这一次的输出就是下一次的输入"：
1. 人写笔记 → AI ingest → AI 生成 wiki 页面
2. 用户提问 → AI 读 wiki → AI 回答 → 好的回答回写 wiki
3. Wiki 页面成为下一次查询的上下文 → 更准确的回答

### 8.2 Karpathy Wiki 文件夹里到底做了什么"特殊处理"？

你问得很好——wiki 文件夹不是简单的"摘要集合"。它有几种特殊页面：

#### 特殊处理 1：Entity Page（实体页）

不是某篇文档的摘要，而是**跨文档的实体画像**。

```markdown
# Obsidian

## 概要
Obsidian 是一款基于本地 Markdown 文件的知识管理工具，支持双向链接和图谱视图。

## 在本知识库中的角色
- 主要 PKB 工具（见 [[PARA-Vault]]）
- 与 AI 系统共享文件夹（见 [[ai-paas 架构]]）
- 使用 Dataview 插件做任务管理（见 [[Dataview 用法]]）

## 关键特性
- 双向链接：[[页面名]]
- 图谱视图：可视化知识网络
- 插件生态：Dataview, Templater, etc.

## 相关文档
- [[Obsidian 安装配置]]
- [[PARA 方法论]]
- [[ai-paas 项目]]
```

**来源**：这个页面不是任何一篇文档的摘要，而是 LLM 读了所有提到 Obsidian 的文档后**综合生成**的。

#### 特殊处理 2：Concept Page（概念页）

解释一个抽象概念，串联所有相关文档。

```markdown
# RAG（检索增强生成）

## 定义
RAG 是一种让 LLM 基于检索到的外部知识回答问题的技术。

## 在本知识库中的应用
- ai-paas 的知识库系统（见 [[vault_rag_design]]）
- 当前问题：500字截断导致信息丢失（见 [[rag-restructure-analysis]]）

## 相关技术
- 向量搜索：[[Vector Search]]
- Chunking：[[文档分块策略]]
- Embedding：[[BGE 模型]]
```

#### 特殊处理 3：Cross-Reference（交叉引用）

Wiki 页面之间的 `[[双向链接]]` 不是随机的，而是 LLM 在入库时**主动建立**的。

**这就是 wiki 比普通 RAG 强的核心原因**：RAG 只做"搜索→回答"，Wiki 做"搜索→回答→建立关联→沉淀"。

#### 特殊处理 4：Index.md（目录索引）

```markdown
# Knowledge Base Index

## 实体
- [[Obsidian]] — 本地知识管理工具，主 PKB
- [[ai-paas]] — 个人 AI 平台项目
- [[Qwen]] — 本地 LLM 模型

## 概念
- [[RAG]] — 检索增强生成技术
- [[Vector Search]] — 向量相似度搜索
- [[Chunking]] — 文档分块策略

## 源文档摘要
- [[vault_rag_design 摘要]] — RAG 系统设计文档
- [[log-DEPLOY-P1 摘要]] — 第一阶段部署记录
```

**LLM 查询时第一个读的就是 index.md**，然后决定需要读哪些页面。

### 8.3 你的"单一文件夹"方案是否可行？

**完全可行，而且比 Karpathy 的三层分离更适合你。**

原因：

| Karpathy 的场景 | 你的场景 |
|---|---|
| 源文档是外部的（论文、网页） | 源文档就在 Obsidian Vault 里 |
| 源文档格式不统一 | 源文档已经是 Obsidian markdown |
| 需要分离"原始"和"整理后" | Vault 本身就是结构化的 |
| Wiki 是对外部知识的消化 | Wiki 可以直接写在 Vault 里 |

**你的方案更简洁**：
- 不需要单独的 wiki 文件夹——wiki 页面直接写在 Vault 的 `_wiki/` 子目录
- Obsidian 可以直接浏览、编辑、搜索 wiki 页面
- Wiki 页面和源文档在同一个图谱里，双向链接天然互通

**需要的区分**只是用目录或 frontmatter 标记：
- 源文档：`tags: [source, human-written]`
- Wiki 页面：`tags: [wiki, ai-generated]`

### 9.1 纯 Wiki 方案（Karpathy 原版，适配到你的场景）

架构：
  源文档（Vault） → LLM 入库处理 → _wiki/ 页面 → 查询时读 wiki 回答
  
索引方式：
  index.md（目录式） + wiki 页面的 [[双向链接]]
  
回答流程：
  用户提问 → 读 index.md → LLM 决定读哪几个 wiki 页面 → 读页面 → 综合回答
```

### 9.2 混合方案（Wiki 思想融入 RAG）

```
架构：
  源文档（Vault） → LLM 入库预处理生成摘要 → 摘要 embedding 入 ChromaDB
                                              → 查询时：向量搜索摘要 → 读原文 → 回答
  
索引方式：
  ChromaDB 向量索引（基于摘要） + 原文文件系统
  
回答流程：
  用户提问 → 向量搜索摘要 → 找到对应原文 → 读完整原文 → Qwen 回答

### 9.6 决策建议

**如果你的核心诉求是"越用越强"——选纯 Wiki。**

**如果你的核心诉求是"先能用起来"——选混合方案。**

混合方案可以分阶段部署，修完 RAG 止血项就立竿见影。Wiki 需要更长的建设周期。

**你的情况**：你说了"初次建立时间几乎无所谓"、"手工梳理也没问题"。这排除了混合方案的唯一优势。那你应该选纯 Wiki。

### 9.7 关于 Obsidian 和 Wiki 共存的实现细节

你说"把人家原先的 wiki 文件夹给干掉了"——其实不需要干掉。可以这样设计：

```
Obsidian Vault/
├── 1_PROJECT/          ← 源文档（人写）
├── 2_AREA/             ← 源文档（人写）
├── 3_RESOURCE/         ← 源文档（人写）
├── 4_ARCHIVE/          ← 源文档（人写）
├── _wiki/              ← AI wiki（LLM 写，人可编辑）
│   ├── index.md        ← 目录索引
│   ├── entity/         ← 实体页
│   ├── concept/        ← 概念页
│   ├── source/         ← 源文档摘要
│   └── synthesis/      ← 综合分析
└── _schema/            ← Agent 行为规范
    ├── ingest.md       ← 入库规则
    ├── query.md        ← 查询规则
    └── lint.md         ← 维护规则
```

**Obsidian 和 AI 系统共享同一个文件夹**：
- Obsidian 读写所有 .md 文件（包括 `_wiki/`）
- AI 系统读所有 .md 文件，只写 `_wiki/` 和 `_schema/`

- Wiki 页面中的 `[[双向链接]]` 在 Obsidian 图谱中可见

**Schema 文件夹的作用**：
- `ingest.md`：告诉 LLM 如何处理新文档（生成什么页面、如何命名、如何交叉引用）
- `query.md`：告诉 LLM 查询时怎么走（先读 index.md、再读相关页面、怎么综合回答）
- `lint.md`：告诉 LLM 怎么做健康检查（检查什么、怎么标记问题）

这些 schema 文件就是 CLAUDE.md 的角色——它们定义了 LLM 的行为规范。未来换模型、换 Agent，只需要改 schema 文件。

| **ai-paas** | AI 平台（Docker 微服务） | vLLM + Router + RAG + Webapp + Whisper + ComfyUI | 你自己 | 生产运行中 |
| **obsidian-nexus** | Obsidian Vault 模板 | PARA 结构 + 日记模板 + 时间追踪脚本 | 开源社区 | v0.7.0 alpha |
| **PARA-Vault** | 个人知识库 | 1,800+ 篇 .md（日记、笔记、技术文档） | 你自己 | 持续增长 |

**关键发现**：三个项目目前完全独立，代码库之间零引用。ai-paas 的 RAG 服务通过 volume mount 读取 PARA-Vault，但不拥有它。

### 11.2 为什么不能把 Wiki 塞进 obsidian-nexus

| 问题 | 说明 |
|---|---|
| **定位冲突** | obsidian-nexus 是给人用的 Obsidian 模板；Wiki 引擎是给 AI 用的后端服务。两者的"用户"完全不同 |
| **数据不匹配** | obsidian-nexus 是空模板（PARA 文件夹全是空的）；Wiki 需要真实内容才能生成页面。把 1800 篇文档放进模板仓库毫无意义 |
| **技术栈不同** | obsidian-nexus 是纯 Markdown + Obsidian 插件（Dataview/Templater）；Wiki 引擎需要 Python + ChromaDB + LLM 推理 |
| **维护负担** | obsidian-nexus 面向社区，需要稳定性；Wiki 引擎是实验性的，迭代频繁。混在一起会互相拖累 |
| **隐私风险** | Wiki 引擎处理你的私人知识库；obsidian-nexus 是公开仓库。代码和数据必须严格分离 |

### 11.3 为什么不能把 Wiki 单独建一个新项目

| 问题 | 说明 |
|---|---|
| **基础设施依赖** | Wiki 引擎需要 LLM 推理（vLLM/Qwen）、向量数据库（ChromaDB）、embedding 模型（BGE）。这些全在 ai-paas 里 |
| **部署复杂度** | 多一个独立项目 = 多一套 Docker Compose、多一个网络、多一套配置。单 3090 机器上跑两套 AI 平台没有意义 |
| **重复代码** | LLM 调用、embedding 生成、Vault 文件读写——这些在 ai-paas 的 RAG 服务里已经实现了 |

### 11.4 最优架构：三层分离，接口连接

│  │  ├─ .obsidian/   │    │                  │                      │

### 11.5 各层职责划分

#### 模板层：obsidian-nexus（公开仓库）

**职责**：提供可复用的 Obsidian 配置和 Wiki Schema 模板

**新增内容**：
```
obsidian-nexus/VaultPARA/
├── .obsidian/           ← 现有：Obsidian 配置
├── 3_RESOURCE/          ← 现有：模板和脚本
└── _schema/             ← 新增：Wiki 行为规范模板
    ├── ingest.md        ← 入库规则（如何处理新文档）
    ├── query.md         ← 查询规则（如何回答问题）
    └── lint.md          ← 维护规则（如何做健康检查）
```

**为什么不放 wiki 页面**：
- `_schema/` 是"规则"，可以标准化、可以共享、可以版本控制
- `_wiki/` 是"数据"，每个人的 wiki 内容完全不同，不能标准化
- obsidian-nexus 的用户克隆后，得到的是 schema 模板，他们用自己的 Vault 内容生成自己的 wiki

**对社区的价值**：
- obsidian-nexus 从"PARA 日记模板"升级为"AI-ready PARA 模板"
- 用户克隆后，schema 文件告诉 AI 系统怎么处理他们的 Vault
- 不绑定任何特定 AI 引擎——schema 是纯 Markdown，人可读，AI 也可读

#### 引擎层：ai-paas（私有仓库）

**职责**：运行 Wiki 引擎，处理 LLM 推理

**新增/改造内容**：
```
ai-paas/services/rag/app/
├── rag_engine.py        ← 现有：保留作 fallback
├── wiki_ingest.py       ← 新增：读源文档 → 生成 wiki 页面
├── wiki_query.py        ← 新增：读 wiki → LLM 综合回答
├── wiki_lint.py         ← 新增：一致性检查、过时标记
└── wiki_schema.py       ← 新增：读取 _schema/ 规范文件
```

**docker-compose.yml 改造**：
- RAG 服务的 volume mount 从"只读 Vault"改为"读写 Vault"
- 环境变量新增 `WIKI_SCHEMA_PATH`（指向 `_schema/`）

**为什么不把引擎代码放进 obsidian-nexus**：
- 引擎是 Python/Docker 后端，和 Obsidian 模板不是一个技术栈
- 引擎依赖 ai-paas 的基础设施（vLLM、Router、ChromaDB）
- 引擎处理的是你的私人数据，不应该在公开仓库里

#### 数据层：PARA-Vault（你的 1800+ 篇文档）

**职责**：存储你的全部知识，包括人写的和 AI 生成的

**新增内容**：
```
PARA-Vault/
├── 1_PROJECT/           ← 现有：人写
├── 2_AREA/              ← 现有：人写
├── 3_RESOURCE/          ← 现有：人写
├── 4_ARCHIVE/           ← 现有：人写
├── _schema/             ← 新增：从 obsidian-nexus 复制（或 symlink）
│   ├── ingest.md
│   ├── query.md
│   └── lint.md
└── _wiki/               ← 新增：AI 生成，人可编辑
    ├── index.md         ← 目录索引
    ├── entity/          ← 实体页（项目、工具、人物）
    ├── concept/         ← 概念页（技术概念、方法论）
    ├── source/          ← 源文档摘要
    └── synthesis/       ← 综合分析
```

**为什么 `_schema/` 要复制到 PARA-Vault**：
- ai-paas 的 RAG 服务只 mount 了 PARA-Vault，看不到 obsidian-nexus
- Schema 文件需要在 Vault 内部，引擎才能读取
- 复制后你可以在 Vault 内微调 schema（比如为特定项目添加特殊规则）
- 未来可以用 symlink 保持同步，或用脚本自动复制

### 11.6 数据流：一次完整的 Wiki 查询

```
1. 用户在 Webapp 输入问题
   ↓
2. Webapp → Router → RAG 服务
   ↓
3. RAG wiki_query 读取 PARA-Vault/_schema/query.md（了解查询规则）
   ↓
4. 读取 PARA-Vault/_wiki/index.md（目录索引）
   ↓
5. LLM 判断需要读哪几个 wiki 页面
   ↓
6. 读取 PARA-Vault/_wiki/entity/xxx.md、concept/xxx.md 等
   ↓
7. LLM 综合回答（带来源引用）
   ↓
8. 返回给用户（15-25 秒）
```

### 11.7 数据流：一次完整的 Wiki 入库

```
1. 你在 Obsidian 写了一篇新笔记（或修改了现有笔记）
   ↓
2. ai-paas 检测到文件变更（inotify 或定时扫描）
   ↓
3. RAG wiki_ingest 读取 PARA-Vault/_schema/ingest.md（了解入库规则）
   ↓
4. LLM 读取新文档全文
   ↓
5. LLM 生成/更新：
   - PARA-Vault/_wiki/source/xxx-摘要.md（源文档摘要）
   - PARA-Vault/_wiki/entity/xxx.md（相关实体页）
   - PARA-Vault/_wiki/concept/xxx.md（相关概念页）
   - PARA-Vault/_wiki/index.md（更新目录）
   ↓
6. 追加 PARA-Vault/_wiki/log.md（操作日志）
```

### 11.8 对 obsidian-nexus 项目的增强

把 Wiki Schema 纳入 obsidian-nexus 后，项目定位从"PARA 日记模板"升级为"AI-ready 知识管理模板"：

| 维度 | 现在 (v0.7.0) | 升级后 |
|---|---|---|
| **定位** | PARA 日记 + 时间追踪 | AI-ready 知识管理平台 |
| **AI 集成** | 仅"复制 prompt"按钮 | 完整的 Wiki Schema（ingest/query/lint） |
| **对社区的价值** | 好用的 Obsidian 模板 | 好用的模板 + AI 知识管理范式 |
| **差异化** | 类似模板很多 | "AI-native Obsidian Vault" 概念独特 |
| **README 卖点** | "Automated PARA Journal" | "AI-Native PARA Knowledge System" |

**对社区用户的意义**：
- 克隆 obsidian-nexus → 得到 PARA 结构 + 日记模板 + Wiki Schema
- 连接自己的 AI 后端（不一定是 ai-paas，任何支持文件读写的 AI 系统都可以）
- Schema 是纯 Markdown，不绑定特定技术栈
- 用户可以用 Claude、GPT、本地 LLM——schema 定义的是"行为规范"，不是"技术实现"

### 11.9 实施路径

#### 阶段 0：Schema 设计（1-2 天）

在 ai-paas 内部先设计好 schema 内容：
1. 设计 `ingest.md`：定义 LLM 如何处理新文档（生成什么页面、如何命名、如何交叉引用）
2. 设计 `query.md`：定义 LLM 查询时怎么走（先读 index.md、再读相关页面、怎么综合回答）
3. 设计 `lint.md`：定义 LLM 怎么做健康检查（检查什么、怎么标记问题）

#### 阶段 1：PoC 验证（3-5 天）

在 PARA-Vault 内手动走一遍：
1. 创建 `_schema/` 和 `_wiki/` 目录
2. 用一篇具体文档手动执行 ingest（不写代码，直接让 Qwen 按 schema 生成）
3. 验证 wiki 页面质量
4. 手动执行 query，验证回答质量
5. 根据结果调整 schema

#### 阶段 2：引擎开发（2-3 周）

在 ai-paas 内开发 Wiki 引擎：
1. `wiki_ingest.py`：自动化入库流程
2. `wiki_query.py`：自动化查询流程
3. `wiki_lint.py`：健康检查
4. 改造 RAG 服务的 API 端点
5. 改造 Webapp UI

#### 阶段 3：obsidian-nexus 升级（1 周）

Schema 稳定后，反哺到 obsidian-nexus：
1. 将 `_schema/` 模板文件添加到 `VaultPARA/`
2. 更新 README，说明 AI 集成能力
3. 发布新版本（v0.8.0 或 v1.0.0）

#### 阶段 4：全量入库（持续）

1. 分批处理 1,800 篇文档（每天 100 篇，约 2 周）
2. 持续优化 schema 和 prompt
3. 新文档入库时自动生成 wiki

### 11.10 一句话总结

**ai-paas 是引擎，obsidian-nexus 是蓝图，PARA-Vault 是地基。** Wiki Schema 作为蓝图从 obsidian-nexus 分发，Wiki 引擎在 ai-paas 中运行，Wiki 页面在 PARA-Vault 中生成。三者各司其职，通过 `_schema/` 这个接口连接。
